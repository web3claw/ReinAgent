## 三、 已被推翻与封存的歧途（严禁重复研究）

### 1. 歧途一：死磕 HTTP 私有传输层加解密（`d.c` / `d.b` / `X-Seed` / `X-Hash`）
- **现象与浪费轮次**：远端在 `task-1792414088636-h92ti` 连续花了近 40 轮，尝试了 AES-CTR、AES-GCM、XChaCha20、ChaCha20、HChaCha20，试图黑盒拟合 HTTP 请求体 `d.c` 的 16 字节头部与 Nonce 派生规则，全量覆盖尝试均未命中。
- **本质定论**：`d.c` / `d.b` 是旺商聊私有的 HTTP 网络封包层（静态链接在 `libsecurity.so` / `xclient.node` 内部且 JNI 表动态填充）。
- **避坑决策**：**立即彻底封存并终止 HTTP 传输层逆向**！云信官方长连根本不走这层私有 HTTP 传输层，绕过它直接走云信长连。

### 2. 歧途二：依赖 `xclient.node` 引擎或 Frida 注入发消息
- **现象**：此前远端曾通过挂载 `xclient.node` 引擎或用 Frida hook 注入客户端发消息拿到了 `serverId`，并宣称“发消息已跑通”。
- **避坑决策**：严禁偷梁换柱！`xclient.node` 内存占用大、易多开崩溃；Frida 属于外挂注入，不符合客户独立纯协议挂机交付标准，已物理封杀。

### 3. 歧途三：命令行裸跑交互式 `frida.exe` 导致死锁
- **现象**：在 PowerShell 中执行 `frida.exe -U -p $p -l trigger_poll.js -q`，因无超时机制导致命令卡死 10 分钟以上，触发超时告警。
- **避坑决策**：若需要动态取样，必须使用 Python 超时退出脚本（`session.detach()` + `time.sleep(2)`），严禁在 shell 中裸跑。

## 四、 当前最高效的破局实施路线（云信官方 C SDK 方案）

### 核心逻辑
1. 旺商聊本质是基于网易云信（NIM）开发的即时通讯软件；
2. 服务端与客户端的长连交互采用网易云信官方协议；
3. **网易云信官方 Windows C SDK (`nim_c_sdk.dll`)** 是官方提供的纯底层网络库（仅维持 TLS Socket、心跳与消息事件，纯 C 接口，体积几 MB，单账号内存 3~5MB）；
4. **落地步骤**：
   - **步骤 1**：在工程中引入网易云信官方 Windows SDK（`nim_c_sdk.dll`）；
   - **步骤 2**：通过 Python `ctypes` 或 Node `koffi` 加载 `nim_c_sdk.dll`；
   - **步骤 3**：传入已捕获的 `app_key`、`accid`（如 `1195425452`）与云信 Token 调用 `nim_client_login`，直接建立长连；
   - **步骤 4**：注册消息接收回调，长连推过来的即是带有 `body.b` 的群消息，直接调用已攻克的 `ChaCha20-Poly1305 draft-agl` 还原明文（**收群消息 100% 闭环**）；
   - **步骤 5**：发群消息时，先生成 Ed25519 签名与 `CMessage` 加密体，调用 `nim_talk_send_msg` 塞入长连发出（**发群消息 100% 闭环**）。
